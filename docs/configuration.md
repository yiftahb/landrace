# Configuration

A project's Landrace settings live in its **workspace**, the `.landrace/` folder: `landrace.yaml` for how Landrace runs, and `.env` for secrets. The workflows themselves are described in [Workflows](workflows.md).

## landrace.yaml

`.landrace/landrace.yaml` holds the runtime: how agents run and where items live. A workflow keeps none of this, so one workflow carries from project to project.

Every key, with its default:

| Key | Default | Meaning |
|---|---|---|
| `version` | — (required) | Always `1` |
| `agent.adapter` | — (required) | The executor that runs steps and conversation turns: an id a hook registers with `defineExecutor`. The shipped ones are `claude` and `codex` — see [Integrations](integrations.md#claude-code) |
| `agent.isolation` | `worktree` | How the engine prepares the folder a step runs in: `worktree`, or `none` to run the agent in this checkout. A stage that names a `branch` needs `worktree`. The schema also accepts `container`, but it is not implemented: `landrace start` and `landrace mcp` refuse it |
| `agent.signature` | `true` | Whether text an agent writes ends with a line naming its model and effort, such as `// Generated by AI (claude-opus-5-5:medium)`. `false` turns it off. See [What an agent signs](workflows.md#what-an-agent-signs) |
| `agent.worktree.copy` | `[]` | Untracked or ignored files copied from your checkout into a write step's worktree, as globs from the repository root — see [A write step's worktree](#a-write-steps-worktree) |
| `agent.worktree.setup` | `[]` | Commands run in a write step's worktree before its agent, when the lockfiles have changed — see [A write step's worktree](#a-write-steps-worktree) |
| `agent.worktree.lockfiles` | the three root lockfiles | Globs, from the repository root, of the lockfiles whose change runs `setup` again — see [A write step's worktree](#a-write-steps-worktree) |
| `agent.worktree.setupTimeout` | `15m` | How long each setup command may run, as a [duration](#durations) |
| `agent.*` (any other key) | — | Passed unread to the executor `agent.adapter` names. The shipped executors' keys are below |
| `tracker.*` | `{}` | Passed unread to the hooks. The GitHub integration reads `tracker.repo` and `tracker.bot` — see [Integrations](integrations.md#github) |
| `branch` | `landrace/{item}` | The branch each item's work is on. `{item}` is the item's id as the tracker gives it, unchanged, so a Jira key stays uppercase. The forges tie a pull request to an item only by this branch, and every workflow's `branch` lines must name it. `validate` and `start` refuse a template that names `{item}` other than exactly once, has no fixed text before `{item}`, names any other `{placeholder}`, or that git would refuse as a branch once `{item}` is filled with an id — see [The item's branch](workflows.md#the-items-branch) |
| `branchVariants` | `[]` | Names of variants of the item branch: each is `<branch>-<name>`, such as `landrace/{item}-retro` for `retro`. A stage may work on a variant beside the item branch, and the forges tie a pull request from one to its item as they do the item branch's. A name is lower-case letters and digits only, and is named once. `validate` and `start` refuse any other — see [Branch variants](workflows.md#branch-variants) |
| `tick.interval` | `60s` | How often a tick runs, as a [duration](#durations) |
| `tick.concurrency` | `3` | How many agents run at once across the whole workspace, overlapping ticks, every workflow and every person's runtime included: one cap the [roster](architecture.md#the-roster-one-runner-many-people) shares. While several people are asking, each may hold up to this number divided by how many are asking, rounded up; a person asking alone may take every slot. Only a step's agent takes a slot. Checking an item, entering a stage and its effects, and a merge take none, so they go on while agents fill every slot. Each tick checks every claimed item once, most urgent first, and checks at most this many at a time. A step that finds no slot free is left owed, and its row reads `waiting for a free agent slot (tick.concurrency N)`. The next slot a run frees goes to the most urgent item turned away like this — with several people, the most urgent of the next person in turn whose share allows one; otherwise a later tick runs it. A tick that starts while an earlier one is still checking is skipped. A pairing or an MCP conversation turn takes no slot |
| `security.screen` | `true` | Screen each prompt for injection before running an agent that can act — see [Security](security.md#screening-prompts) |
| `security.adapter` | `agent.adapter` | The executor that screens: an id a hook registers with `defineExecutor`. It must run the screener with no tools, or refuse |
| `security.model` | none | The model the screening run asks for. Absent, the screening executor's own default decides |
| `serve.host` | `127.0.0.1` | The address the board and its MCP endpoint bind. Loopback only — see [The front door](#the-front-door) |
| `serve.port` | `4545` | Their port. `landrace start --ui-port` wins over it |
| `serve.publicUrl` | none | An `http://` or `https://` URL a proxy of your own serves the board at — see [The front door](#the-front-door) |
| `log.redact` | `[]` | Names of secrets whose values are cut from every log line and event. Each must name a declared secret whose value is 8 characters or longer, or `landrace start` refuses. A secret not named here is not redacted from the log |
| `secrets.*` | `{}` | Values handed to hooks, usually `$VAR` references resolved from [`.env`](#env), or each person's own — see [Per-person keys](#per-person-keys) |
| `workflows` | by each workflow's `name`, then folder id, by code point | The order the MCP lists workflows in, and the board's sidebar and `/board` tabs show them in. Display only. When given, it must name exactly the folders under `workflows/`: a name with no folder, a folder not named, or a name twice is refused |
| `vars.*` | `{}` | Values substituted into the workflow files — see [vars](#vars), or each person's own — see [Per-person keys](#per-person-keys) |
| `people.local.email` | none | Your email, stamped on every event `landrace start` logs as `personEmail` — see [people](#people) |
| `people.local.name` | none | Your name. Read and resolved, but stamped on nothing yet |
| `people.oidc` | none | The OpenID Connect provider people sign in with. Set, the instance is remote — see [Remote mode](remote.md) |
| `people.overrides` | none | By email, identity values pinned for a person a lookup cannot find — see [Remote mode](remote.md#identities) |
| `people.allow` | none | Who a remote instance admits: each an email, or `@domain` for a whole domain. Required with `people.oidc` — see [Who can sign in](remote.md#who-can-sign-in) |
| `notify.on` | none | The events to tell a person about. There is one: `needs-you` |
| `notify.via` | none | Notifier ids, each registered by a hook with `defineNotifier`. The shipped one is `slack` |

### The agent block

Both shipped executors, Claude Code and Codex, read these `agent.*` keys and refuse any other at startup:

| Key | Default | Meaning |
|---|---|---|
| `agent.model` | the agent's own default | The model every step and turn asks for. A step's own `model` wins |
| `agent.effort` | the agent's own default | How hard the agent thinks, for every step and turn (never the screener). A step's own `effort` wins. Claude takes `low`, `medium`, `high`, `xhigh` or `max`; Codex takes `none`, `low`, `medium`, `high` or `xhigh` |
| `agent.mcp` | `[]` | The MCP servers a step or turn may use. Each entry is a server name, or `{ name, tools }` to allow only some of its tools. A step's own `mcp` narrows it — see [Workflows](workflows.md#step-files) |
| `agent.sandbox.hosts` | `[]` | The only hosts a write step's commands may reach |
| `agent.sandbox.deny` | `[~/.config/gh, ~/.ssh, ~/.aws, ~/.npmrc]` | Paths under your home that a write step may not read. A list you write replaces the default |
| `agent.git` | none | `{ name, email }`: who every commit an agent makes names as author and committer, in place of the `user.name` and `user.email` your `~/.gitconfig` or the repository's config gives. Both keys are required, as non-empty text, written literally or as a `$VAR` or `${VAR}` reference — see [Who commits](#who-commits); any other key or shape is refused at startup. It sets `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL` for every step and turn, which git ranks above every config file. A commit's signing key still comes from your own git config. A hook that commits names it only by passing `gitIdentityEnv(ctx)` to its own git — see [Hooks](hooks.md#the-kits-functions). Unset, git picks the identity as it would for you |
| `agent.plugins` | `[]` | Claude Code only: the plugins a step runs with, unless it lists its own `plugins`. No step loads the plugins you enabled for yourself. Codex refuses it |

What these keys do to a run — which servers a step gets, what the sandbox allows and refuses — is in [Security](security.md#mcp-servers-a-step-may-hold) and [Security](security.md#a-write-steps-sandbox); how each executor applies them is in [Integrations](integrations.md#claude-code).

An `agent.mcp` entry names a server defined in the repository root's `.mcp.json`. A tool name follows the same rule as a server name — letters, digits, `.`, `_` and `-`. An entry with an empty `tools` list, or a server named twice, is refused. This repository's own configuration allows the code graph's reading tools and nothing else:

```yaml
agent:
  mcp:
    - name: codebase-memory-mcp
      tools: [search_graph, trace_path, get_code_snippet, query_graph, get_architecture,
              search_code, get_graph_schema, index_status, list_projects, index_repository]
```

`landrace start` and `landrace mcp` refuse to start — and `landrace validate` reports the same — when `agent.mcp` names a server but the repository root has no `.mcp.json`, when a name is not in it (the refusal lists the names it does define), or when a name is Landrace's own operator server. `landrace status` runs no step and needs no `.mcp.json`.

### Who commits

`agent.git` names who an agent's commits are by. Written literally, it is the same for everyone who runs Landrace on the repository, since `landrace.yaml` is committed:

```yaml
agent:
  git: { name: landrace, email: landrace@example.com }
```

The identity usually goes with the forge token, and each developer's instance has its own token. Write `$VAR` or `${VAR}` instead, and each instance sets its own values in `.landrace/.env`. One developer then runs with a bot's token and bot commits, another with their own token and their own name:

```yaml
# landrace.yaml — the same file for everyone
agent:
  git: { name: $LANDRACE_GIT_NAME, email: $LANDRACE_GIT_EMAIL }
```

```dotenv
# .landrace/.env — each developer's own values
LANDRACE_GIT_NAME=Ann Example
LANDRACE_GIT_EMAIL=ann@example.com
```

A reference resolves at load, from `.env` first and then your shell, exactly as a secret does. A hook's `ctx.config.agent.git` holds the resolved values, never the reference. A variable that is set nowhere, or set to an empty value, is reported by `validate` under `vars`, naming the key and the variable, and `landrace start` and `landrace mcp` refuse to start over it.

### A write step's worktree

A step runs in a fresh checkout under the temporary folder, which holds tracked files only. `agent.worktree` gives a write step's worktree what your project needs to build and test that git does not track:

```yaml
agent:
  worktree:
    copy: ["**/.npmrc", "**/.env"]
    setup: ["pnpm install --frozen-lockfile --prefer-offline"]
    lockfiles: ["pnpm-lock.yaml", "*/pnpm-lock.yaml"]
    setupTimeout: 15m
```

- **`copy`** copies the files each glob matches from your checkout into the worktree, at the same paths, before every write step. Only untracked or ignored files are copied. A glob that matches a tracked file, an absolute path or one with `..` is refused at start, naming the file. A file the item's branch tracks is refused before the step, too, so the branch's own version is never replaced. A link that leads outside the repository is not followed.
- **`setup`** runs each command, in order, in the worktree, after `copy` and before the agent. It runs through your shell, outside the agent and its sandbox, with the same minimal environment the agent gets, less `agent.git`'s identity. A private registry's token reaches it through a copied file such as `.npmrc`.
- **`lockfiles`** decides when `setup` runs again in a kept worktree: globs, from the repository root, of the lockfiles hashed together with the commands. The default is the three root lockfiles, `pnpm-lock.yaml`, `package-lock.json` and `yarn.lock`. A monorepo whose workspaces lock their own dependencies, such as `backend/pnpm-lock.yaml`, lists those too, or `**/pnpm-lock.yaml`. A glob matches the worktree's files that git tracks or does not ignore, so a lockfile a step adds or removes counts as a change. An absolute glob, or one with `..`, is refused at start.
- **A failure or a timeout** stops the item before the agent runs, with the end of the command's output as the reason. Nothing is recorded, so the next tick tries again.
- **Events:** `worktree.setup.started`, `worktree.setup.finished` and `worktree.setup.failed`, each naming the item and the command.
- `copy`, `setup` and `lockfiles` need `agent.isolation: worktree`; `landrace start` refuses them otherwise.

A write step's worktree is kept between the item's write steps on the same branch, and removed when the item reaches a terminal stage. The next tick also removes it once the item is closed, for example by its merged pull request. A write step on a stage that names no `branch` gets `copy` and `setup` too, in a worktree removed when the run ends. Between runs the kept worktree is detached from the branch, so you can check the item's branch out in your own checkout while the item waits; switch back off it before the item's next write step, which halts while the branch is checked out elsewhere. On reuse it is put back on the branch and reset to the branch's commit: what a step left uncommitted is removed, and what git ignores, such as `node_modules`, stays. `setup` runs again only when its commands, or the files `lockfiles` matches, have changed since it last passed. A worktree that is missing, or on another branch, is rebuilt, and setup runs again.

What this exposes to a step is in [Security](security.md#copied-files-and-setup).

### The front door

`landrace start` serves the board and the [operator server](cli.md#the-operator-server) on one port, at `/` and `/mcp`:

```yaml
serve:
  host: 127.0.0.1
  port: 4545
  publicUrl: https://board.example.org/
```

- **`host`** must be loopback — `127.0.0.1` or any `127.x.x.x`, `localhost`, or `::1` — unless [`people.oidc`](#people) is set. Without it nothing asks who a caller is, so a door the network can reach hands anyone every item and the loop's controls. `validate` reports any other host, `0.0.0.0` included, as `serve.unauthenticated`, and `start` refuses it. With `people.oidc`, everyone signs in, and any host is allowed.
- **`port`** is the port both are served on. `--ui-port` wins over it for one start.
- **`publicUrl`** is where a person reaches the board through a proxy of their own that forwards to `host` and `port`. `start` prints it as the board's URL, a notification links to it, and the door answers its host name too. Without `people.oidc`, Landrace does not check who the proxy lets through. With it, `publicUrl` is required and must be `https` unless its host is loopback; `validate` reports either as `serve.public-url`, and `start` refuses it.

Any other key under `serve` is refused. A step is kept from the door whatever these say: see [Security](security.md#the-front-door).

### notify

With a `notify:` block, an item that comes to rest in Needs you is announced once through each notifier `via` names:

```yaml
notify:
  on: [needs-you]
  via: [slack]
```

The message reads `#29 needs you in <workflow> — <title> · <why>`, where `<workflow>` is the name of the workflow that owns the item and `<why>` is the board's note for it (`waiting on you`, `blocked by a security check`, …). Needs you is the board's own rule, so the two never disagree.

- An item that stays in Needs you is not announced again; one that leaves and comes back is.
- An item that arrives at a `waits: person` or `waits: pairing` stage placed by its own state is announced by the tick, after its pass, when it settled there on its first pass or its lock was held elsewhere. A stage placed by a label is announced on the transition into it.
- A tick whose pass halts, fails or moves the item on announces nothing, and the next tick that finds it waiting announces it.
- Nothing is kept about what was sent. After a restart — and on every `start --once`, which is a process of its own — each item already waiting at a stage placed by state is announced once more.
- An item passing through `triage` on its way back is never announced: `triage` runs its step at once.
- Sending is fire and forget. A notifier that fails is a `notify.failed` line in the log, and it never stops an item.

`start` refuses, and `validate` reports, a `via` id no loaded notifier answers to. Writing a notifier is in [Writing an integration](hooks.md#notifiers); Slack's setup is in [Integrations](integrations.md#slack).

### people

`landrace start` runs for one person, `local`. Every event it logs carries `person: "local"`: its own, every hook's, and each workflow's. A workflow's events also carry `workflow`, its folder id. To put your email on them too, name it under `people.local`:

```yaml
people:
  local:
    email: $LANDRACE_EMAIL
```

Each value is written literally or as a `$VAR` or `${VAR}` reference, resolved at load from `.env` first and then your shell, as [`agent.git`](#who-commits)'s is. Every event then carries `personEmail` as well. A reference set nowhere, or set to an empty value, is reported by `validate` under `people.local.email` (or `people.local.name`), naming the variable, and `landrace start`, `landrace status` and `landrace mcp` refuse to start over it. Without a `people` block, events carry `person` and no email. Any key other than `email` and `name` is refused.

`landrace status` stamps its events the same way. `landrace mcp` stamps nothing.

To run one instance for a team, set `people.oidc` to the provider everyone signs in with, `people.allow` to who may sign in, and optionally `people.overrides`:

```yaml
people:
  oidc:
    issuer: https://id.example.org/realms/team
    clientId: landrace
    clientSecret: $LANDRACE_OIDC_SECRET
  allow:
    - ann@example.com
    - "@example.com"
  overrides:
    bob@example.org:
      github: { login: bob-gh }
```

- **`issuer`** is the provider's issuer URL: `https`, or `http` on loopback only.
- **`clientId`** and **`clientSecret`** are what the provider issued this instance. Each may be a `$VAR`, resolved as `people.local`'s are; one that does not resolve is reported as `people.oidc.clientId` or `people.oidc.clientSecret`. The secret is kept out of every log line.
- **`allow`** lists who may sign in: an email such as `ann@example.com`, or `@` and a domain such as `@example.com` for every email at that domain, never its subdomains. Case is ignored. Any other entry, such as `*` or `example.com`, is refused when the file loads. With `people.oidc` set and `allow` missing or empty, nobody is admitted: `validate` reports `people.allow` and `start` refuses. How it is applied, and how it removes a person, is in [Who can sign in](remote.md#who-can-sign-in).
- **`overrides`** maps an email to connection ids, each to the identity fields to store for that person.

With `people.oidc` set, `people.local` is not used, and every event carries the signed-in person's id and email instead. Setup and behaviour are in [Remote mode](remote.md).

### vars

`vars` lets one workflow serve several instances — say, one per developer, each working the items assigned to them:

```yaml
vars:
  assignee: $LANDRACE_ASSIGNEE
  team: platform
```

Wherever `{vars.<name>}` appears in `workflow.yaml` or a step file — a condition, an effect field, a prompt — it is replaced at load with the resolved value. Everything downstream then sees a literal, exactly as if it had been typed: the schema, the operator allowlist, `validate`'s path coverage and the condition itself.

Substitution walks the parsed YAML, never its text, so a value with a colon, a newline or a quote lands in one string and stays one string. It fills in `{vars.…}` and nothing else: `{round}`, `{stage}` and `{node.title}` belong to the engine and survive untouched. Values are strings.

Vars are configuration, not state. They do not vary per item, so they are not in the snapshot.

Every mistake is a load error, never a default:

- a var that does not resolve, or resolves to an empty value, is refused by name — a condition filled in with nothing matches no item, which is the hardest failure there is to read;
- a `{vars.x}` nothing defines is refused, naming the variable, the file and the field;
- a `vars` entry nothing references is refused too — usually the same typo seen from the other end.

**Vars are not secrets.** A secret is handed to a hook, cut by value from the text Landrace composes itself, and — when `log.redact` names it — cut from the log; what is and is not scrubbed is under [.env](#env). A var is substituted into the workflow, so it reaches tracker comments, agents' prompts and the events recording both, with nothing redacting it. `validate` reports, and `start` refuses, a var whose value equals a declared secret's.

**Several developers, one repository.** Each instance exports its own assignee, and the workflow filters on it:

```yaml
# landrace.yaml — differs per developer, through the environment
vars:
  assignee: $LANDRACE_ASSIGNEE
```

```yaml
# workflow.yaml — the same file for everyone
eligible:
  - when: { "node.state.assignees": { $in: ["{vars.assignee}"] } }
    else: "assigned to somebody else"
```

An item assigned to somebody else is skipped, with that `else` as the reason `landrace status` prints, and nothing is written to it. An item assigned to nobody is skipped by everybody rather than worked by everybody, because `node.state.assignees` is an empty list, never absent. The skip costs nothing per item: `list()` already carries every item's assignees, so the rule is answered before any item is read and before any lock is taken. It is still answered after the list, though, so it cannot keep a list under its bound. On a Jira project too large to list whole, scope the tracker itself with the `jiraAssignee` secret; see [One developer's issues](integrations.md#jira).

### Per-person keys

A `secrets` or `vars` entry can be each person's own instead of one value in `.env`. Write it as an object:

```yaml
secrets:
  githubToken: { perPerson: true, env: GITHUB_TOKEN, connection: github.token }
```

- `perPerson` is `true`, always.
- `env` is optional. It is a bare variable name, never a `$VAR` and never a value, so the file holds no literal.
- `connection` is `<connection id>.<field>`: the field of a stored connection that answers the key. A hook defines the connection with [`defineConnection`](hooks.md#connections).

Any other key is refused. For the one local person, `local`, the value comes from:

1. `env`, when the variable is set to something, from `.env` first and then your shell, as a `$VAR` resolves. The key then needs no stored connection, so a setup that already sets the variable runs as before, even when no hook defines its `connection` yet.
2. Otherwise, the connection's field in `~/.landrace/credentials/local.json`.

A key neither answers is reported by `validate` as `connection.missing`, naming the variable and the connection. `landrace status` and `landrace mcp` refuse to start over it in the same words, and so does `landrace start` with `--once` or `--headless`. A `start` that serves a board runs nothing and serves only its Integrations tab, where you paste the value — see [A connection not made](cli.md#landrace-start). A credentials file that cannot be read, or is not the shape below, is `connection.failed`, with the reason. The reason names the file and each wrong key, and never quotes what the file holds, since that could be part of a token. Once the hooks load, `validate` reports and `status` refuses each of the problems below. A `start` that serves a board refuses `connection.unknown` and `connection.duplicate`, and serves only its Integrations tab for the rest:

- `connection.unknown`: a key its variable left unset naming a connection no hook defines, or a field the connection does not list;
- `connection.expired`: a connection older than its `lifetimeDays`, or past its `expiresAt`;
- `connection.failed`: a connection whose stored `failure` says it no longer works, such as a Claude token the agent refused;
- `connection.missing`, `connection.expired` or `connection.failed` for a connection a hook marks `required: always`, whether a key names it or not;
- `connection.expired` or `connection.failed` for any stored connection a hook defines, whether anything requires it or not;
- `connection.duplicate`: two different connection objects with one id, in two workflows' hooks.

`landrace next` fills in a var from the store too.

The credentials file is JSON, mode 0600, in a directory of mode 0700. Replace `your-member-id` with your Slack member id (`U…`, from your profile's ⋮ → Copy member ID):

```json
{
  "person": { "id": "local" },
  "connections": {
    "slack": { "fields": { "userId": "your-member-id" }, "source": "override", "connectedAt": "2026-11-04T09:00:00.000Z" }
  }
}
```

- `person` is `{ id, email?, name? }`. Its `id` must be the file's name.
- Each connection holds `fields`, `source` (`paste`, `oauth`, `lookup` or `override`) and `connectedAt`, an ISO 8601 time.
- A connection may also hold `expiresAt`, `failedAt`, `failure` and `refresh: { token }`. Any other key makes the file unreadable.

The board's [Integrations tab](cli.md#the-board) writes a credential you paste into it, with `source: paste`, and one you connect with its provider, with `source: oauth` — its `expiresAt` the provider's end for it, and its `refresh` the token `start` renews it with (see [Connect with GitLab or GitHub](integrations.md#connect-with-gitlab-or-github)). It removes one you disconnect. An identity cannot be pasted: `start` looks it up by `people.local.email` and writes it with `source: lookup` (see [Connections](hooks.md#connections)). To name one a lookup cannot find, write it by hand, as above, or set the variable. When a step's agent refuses a stored login, or a provider refuses to renew one, `start` adds `failedAt` and `failure` to it. Every value in the file is cut from the log once it is read, if it is 8 characters or longer, and a pasted one before its connection's `check` runs; a per-person secret is also handed to hooks and scrubbed as any secret is (see [.env](#env)). A per-person var is still a var: it reaches comments and prompts unredacted. How runs are kept from reading the file is in [Security](security.md#stored-credentials).

### Durations

`tick.interval`, a workflow's `budget.stepTimeout` and a step's `timeout` are durations: a whole number followed by `s`, `m` or `h` — `60s`, `2m`, `1h`. A bare number is refused, and so is anything above 596 hours.

## .env

`.landrace/.env` holds secrets as `KEY=value` lines. Blank lines and lines starting with `#` are ignored, and a value may be quoted.

```dotenv
GITHUB_TOKEN=ghp_your_token_here
SLACK_WEBHOOK_URL=https://hooks.slack.com/services/T…/B…/…
SLACK_NOTIFY_USER=U0123456789
```

`landrace.yaml` names each secret it wants under `secrets:`, as a `$VAR` or `${VAR}` reference:

```yaml
secrets:
  githubToken: $GITHUB_TOKEN
log:
  redact: [githubToken]
```

The reference is resolved at load, from `.env` first and then your shell — a project's own file wins over whatever is exported in the terminal. The value is handed to hooks; a hook never reads `process.env` itself, which keeps it testable and lets redaction know every value to suppress. Every declared secret of 8 characters or more is cut from the text Landrace composes itself: the failure records it writes on an item (a refused or rejected round's reason), the errors the board's item panel shows, and the agent activity the panel lists. What an agent writes is posted as the agent wrote it, unscrubbed: a step's prose and output through its route (`tracker.comment`, `pull.review`, a published spec), and a conversation's answers. Name a secret in `log.redact` to cut it from the log too. A secret whose variable is set nowhere is reported by `validate`, and `landrace start` and `landrace mcp` refuse to start over it.

`validate` fails if `.env` exists and git does not ignore it. `.landrace/.env.example` lists the variables this repository uses.

## Telemetry

Telemetry is off by default. When it is on, every event — `tick.*`, `step.*`, `effect.*`, `lock.*`, `screen.*`, `notify.*`, `worktree.setup.*`, `agent.limited`, `integration.limited`, `connection.*`, and `agent.event` and `snapshot.built` whether or not `--debug` is on — is sent to an OpenTelemetry collector as a **log record**, the way Claude Code exports its own events.

- The record's body and its `event.name` attribute are the event's name.
- Every other field becomes an attribute prefixed `landrace.` (`landrace.item`; an agent's parsed output in `landrace.event`, and a line of it that was not JSON in `landrace.raw`), JSON-encoded unless it is a string, number or boolean.
- Every event `landrace start` logs carries `landrace.person` (`local`, or on a remote instance the signed-in person's id), and `landrace.personEmail` when [`people.local.email`](#people) is set or the person signed in. A workflow's events carry `landrace.workflow` too.
- `*.failed`, `*.denied`, `*.blocked`, `*.limited` and `lock.stolen` are `WARN`; everything else is `INFO`.

Two events say a limit was hit:

- **`agent.limited`** — `{ item, workflow, stage, round, kind }`. A step's agent failed with text naming a limit. `kind` is `usage` (the plan's usage limit or quota), `rate` (a rate limit, or a 429) or `overloaded` (the provider is overloaded, or a 529). The step is unavailable as before, after its `step.rejected`: it writes no record and counts no round, and the next tick runs it again.
- **`integration.limited`** — `{ integration, status, where, retryAfter? }`. A tracker, forge, docs or notifier integration got a 429 — or, from GitHub, a 403 with `x-ratelimit-remaining: 0`. `where` is the API path it was refused on; Slack's is `webhook`, since its URL is the credential. `retryAfter` is the `Retry-After` header as sent, when there is one. Notion logs every 429 it waits out, not only the last.

Three are about a person's connections:

- **`connection.expiring`** — `{ connection, expiresAt, daysLeft }`. A stored connection has 30 days or fewer left. `start` logs it at most once a day per connection, at the first tick of each UTC day. Not for a connection made by OAuth that holds a refresh token, which `start` renews before its end.
- **`connection.failed`** — `{ item, workflow, stage, round }`. A step's agent refused the person's own stored login, such as a Claude token that has expired. The step is unavailable as before and writes no record; the connection is marked failed, `start` rebuilds its runtime, and nothing runs until it is connected again. With `{ connection, error }` instead, either marking it failed did not work, and why, or renewing an OAuth token failed: refused by the provider, when the connection is marked failed in the same way, or not answered, when the next minute's pass asks again — see [Connect with GitLab or GitHub](integrations.md#connect-with-gitlab-or-github).
- **`connection.refreshed`** — `{ connection, expiresAt? }`. `start` renewed a token made by OAuth before its end, stored it, and handed it to the running hooks. Neither token is in the event.

On a remote instance, `signin.ok`, `signin.refused` and `request.refused` record sign-ins and refused requests — see [Remote mode](remote.md#events).

- Records carry the same redaction as the console. Traces and metrics are not exported.

| Variable | Meaning | Default |
|---|---|---|
| `LANDRACE_ENABLE_TELEMETRY` | `1` turns export on | off |
| `OTEL_LOGS_EXPORTER` | `otlp` or `console` | `otlp` |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf` or `http/json`; `grpc` is refused | `http/protobuf` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | The collector's base URL; `/v1/logs` is appended | `http://localhost:4318` |
| `OTEL_EXPORTER_OTLP_HEADERS` | `k=v,k=v`, for example auth; values are percent-decoded | none |
| `OTEL_SERVICE_NAME` | `service.name` | `landrace` |
| `OTEL_RESOURCE_ATTRIBUTES` | `k=v,k=v`, extra resource attributes | none |
| `OTEL_LOGS_EXPORT_INTERVAL` | Batch delay, in milliseconds | `5000` |

Set them in `.landrace/.env` or your shell (`.env` wins), or on the command line, which wins over both: `landrace start --telemetry` sets `LANDRACE_ENABLE_TELEMETRY=1`, and `--otel KEY=VALUE`, repeatable, sets any key in the table — any other key is a startup error. `landrace mcp` reads `.env` and the shell only, and refuses `OTEL_LOGS_EXPORTER=console`, which would write into its protocol on stdout. `landrace status` never exports.

`landrace start` flushes the batch on `--once`, on a normal stop and on the first Ctrl-C; a second Ctrl-C exits without waiting. An export that fails says so once on stderr, and again only after one has succeeded. None of these variables reach the agent's process: `OTEL_EXPORTER_OTLP_HEADERS` is usually a credential.

To see it work, run a collector with the `debug` exporter on port 4318, then:

```bash
landrace start --once --telemetry
```
