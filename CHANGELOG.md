# Changelog

All notable changes to Landrace are recorded in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- **On Linux, `start` and `validate` check that a write step's sandbox can start.** Claude Code runs a write step's commands in bubblewrap, which needs `bwrap` and `socat` on `PATH`. Ubuntu 24.04 also refuses bwrap a user namespace unless an AppArmor profile allows one. Before, read-only steps ran and every write step failed, one item after another. Now, when a workflow has a `repo:write` step under Claude, `start` refuses and `validate` reports it under `executor`, naming the steps. A missing program says to install bubblewrap and socat. A failed trial `bwrap` run quotes what bwrap printed and gives the AppArmor fix. macOS, Codex and workflows with no write step are not checked. See [A write step's sandbox](docs/security.md#a-write-steps-sandbox) and [Remote mode](docs/remote.md#before-you-start).

### Fixed

- **A Claude step that fails with an empty result says why.** When Claude Code's sandbox cannot start, its result's text is empty and the cause is in its `subtype` and `errors`. Before, the step's reason read `agent reported an error: ` with nothing after it. Now the reason names the `subtype` and each error. A result with text keeps its text as the reason.

## [2.0.2] - 2026-11-08

### Fixed

- **A Jira lookup by email finds a person whose email their profile hides.** Jira Cloud answers a hidden email as an empty string, not by leaving it out. Before, the lookup read that as a different email and dropped the person, so `jiraConnection` said Jira found nobody, and a `jiraAssignee`, mention or user field given that email matched no user. This showed only when another account did the lookup, such as a remote instance's shared Jira account, because Jira always shows you your own email. Now an empty or blank email counts as hidden. An email that matches several users is still refused. See [Jira](docs/integrations.md#jira).

- **The board's header hides the folder chip when there is no folder name.** Before, the chip beside the title drew an empty bordered box. This happened on the remote board, whose view carries no folder name, and on every board load until the first poll landed. Now the chip starts hidden and shows only while the view names a folder.

## [2.0.1] - 2026-11-08

### Fixed

- **Sign-in accepts a provider whose ID token leaves out `email_verified`.** Some OpenID Connect providers, such as Okta's org authorization server, send `email` and `email_verified` only from their userinfo endpoint. Before, remote sign-in refused every person at such a provider as unverified. Now, when the ID token has no `email` or no `email_verified`, Landrace asks userinfo for the missing value. The ID token's own values still win, and userinfo's `email_verified` counts only for the email userinfo names. A userinfo answer about another subject (`sub`), or a failed userinfo request, is refused with `502`. No configuration or scope is added. See [Signing in](docs/remote.md#signing-in).

## [2.0.0] - 2026-11-05

### Breaking

- **The operator server moved from stdio to the board's port.** `landrace start` now serves the MCP tools over Streamable HTTP at `/mcp`, beside the board: `http://127.0.0.1:4545/mcp` by default. A bare `landrace mcp`, as an editor configured before this still runs it, now reads no configuration, prints where the tools moved and exits 1. `landrace mcp` now runs only the stdio servers Landrace starts itself, for a pairing and for a step that creates sub-items. Point the editor at the endpoint instead: for Claude Code, run `claude mcp add --transport http landrace http://127.0.0.1:4545/mcp` while `landrace start` runs. `/mcp?workflow=<id>` scopes a session as `--workflow` once scoped the stdio server, and an id the workspace does not have is refused with `400`. The endpoint answers `421` to a `Host` that is not one of the board's own names, and `403` to an `Origin` from another site. Writes through it wake the loop directly, with no wake file. `--headless` and `--once` serve no endpoint. See [The operator server](docs/cli.md#the-operator-server).
- **`agent.sandbox.hosts` may not name the board's own hosts.** An entry that matches `127.0.0.1`, `localhost` or `serve.publicUrl`'s host, wildcards included, is refused, so a write step's commands cannot reach the operator tools at `/mcp`. `validate` reports it under `executor`, and `start` refuses to start. An `agent.mcp` server whose URL is the door's, at any of its origins or at any loopback address on its port, is refused under any name. The Claude executor also denies every run `WebFetch` of those host names. The Codex executor adds no such deny. See [Security](docs/security.md#the-front-door).
- **Steps are denied more of your secrets.** Under Claude, every step and conversation turn is now denied the `.env` beside `landrace.yaml` and `~/.landrace/credentials`, whatever `agent.sandbox.deny` says. The default `deny` list gains `~/.git-credentials` and `~/.config/git/credentials`, where git's `store` helper keeps passwords, so a step's own git command that authenticated through that helper now gets no password. A list you write still replaces the default, so add them to yours. Read-only steps under Claude now get a `Read` rule for each denied path too; before, only write steps were held to the list. When the path `start` runs from passes through a symlink, the `.env` is also denied by its real path. When the `.env` is itself a symlink, the file it points at is denied too, and one that does not resolve refuses the run. Codex keeps no path rules, so under Codex every step and turn can still read these files. See [The workspace's `.env`](docs/security.md#the-workspaces-env) and [Stored credentials](docs/security.md#stored-credentials).
- **A checkout whose path holds `(`, `)` or a control character runs nothing under Claude.** No deny rule can hold such a path, so each step and turn there is refused, naming the path, rather than left able to read the workspace's `.env`. A write step there is also refused for its [git control paths](docs/security.md#git-write-rules). `~/Projects (old)/app` is such a path. `start` and `validate` do not warn about it. Move or rename the checkout. Codex keeps no path rules, so it still runs read-only steps there while nobody else is on the instance. See [The workspace's `.env`](docs/security.md#the-workspaces-env).
- **Codex runs no step that may write.** No live check has shown that Codex's `workspace-write` sandbox keeps a command from git's control paths, so the Codex integration does not declare `keepsDenyWrite`. `validate` and `start` now refuse each `repo:write` step under Codex, naming it, the shipped `build`, `fix-review` and `retro` steps included. Under Codex, run only read-only steps. Every agent integration built on `BaseExecutor` follows the same rule: without `protected readonly keepsDenyWrite = true`, it refuses each step that may write, and refuses a write run handed any path. While the credentials key is a systemd credential, Codex refuses every run, since it cannot keep a command from the key's folder. See [Codex](docs/integrations.md#codex) and [BaseExecutor](docs/hooks.md#baseexecutor).
- **`start` asks the operating system's secret store for a key.** Every `start` now looks for the key that seals the files under `~/.landrace/credentials/`, before it reads any of them, whether or not you store anything there. On macOS it looks in the login Keychain and, the first time, adds an item there, service `landrace` and account `credentials-key`. On Linux with `DBUS_SESSION_BUS_ADDRESS` set and `secret-tool` installed, it does the same in the Secret Service. A lookup that fails for any reason other than the key's absence refuses the start. When `CREDENTIALS_DIRECTORY` is set, as systemd sets it for a unit that loads any credential, `start` reads the key from the file `landrace-credentials-key` there, never makes one, and refuses to start when that file is missing; load one with `LoadCredentialEncrypted=`. With no secret store, as on Windows, `start` says so in one line and keeps the files as plain JSON. See [Sealed at rest](docs/security.md#sealed-at-rest).
- **Landrace's own git runs none of your hooks.** Every git command Landrace starts, the kit's `gitIn` included, now carries `-c core.hooksPath=/dev/null -c core.fsmonitor=false`. So a hook of yours, such as a `post-checkout` hook, no longer runs when Landrace cuts a worktree, and a hook module that commits through `gitIn` runs no `pre-commit` hook. Git LFS's hooks are off too; its filters still run, since they are configuration. See [Git write rules](docs/security.md#git-write-rules).

### Added

- **`serve: { host, port, publicUrl }`** in `landrace.yaml`: where the board and its MCP endpoint bind, and the URL a proxy of your own serves them at. Without `people.oidc`, `host` must be loopback: `validate` reports any other, `0.0.0.0` included, as `serve.unauthenticated`, and `start` refuses it. `port` defaults to `4545`. `--ui-port` no longer has a default of its own, and wins over `serve.port` for one start. The door answers only its own host names: `127.0.0.1` and `localhost` on its port, the host it bound, and `publicUrl`'s host. Any other `Host` gets `421`. See [The front door](docs/configuration.md#the-front-door).
- **Remote mode: one instance for a team.** With `people.oidc` set to an OpenID Connect provider's `issuer`, `clientId` and `clientSecret`, one `landrace start` serves everyone `people.allow` admits, behind a TLS proxy of your own. `people.allow` lists emails, or `@domain` for every email at that domain and not its subdomains, ignoring case. Sign-in uses PKCE and needs an email the provider marks verified. The session cookie is `HttpOnly` and `SameSite=Lax`, named `__Host-landrace_session` over `https`, and sessions live in memory for 12 hours. Each person whose connections are ready gets a runtime of their own: their own board, MCP sessions, worktrees and agent activity, events stamped with their id and email, and sub-items filed with their own connections. A per-person key's `env` variable is ignored; each person's value comes from their own connection. An identity is looked up by the email the person signed in with, and is never given to two people. `people.overrides` pins one by email. A Codex step runs on the operator's own Codex login. An item two people's runtimes claim is worked by neither, and `item.ambiguous` names both. A tick on which any person's listing fails starts no new run for anyone, and logs `source.failed`. `tick.concurrency` stays one cap over everyone's agents: while several people are asking, each may hold the cap divided by how many are asking, rounded up. Pairing is off. To remove someone, take them off `people.allow` and restart `start`: every session, MCP code and token of theirs is then refused. `validate` and `start` refuse a remote instance with no `people.allow`, a `serve.publicUrl` that is missing or plain `http` off loopback (`serve.public-url`), or `agent.isolation: none`. `validate` also prints each signed-in person's own connection problems, and a `warning:` for each secret written as a plain string and each per-person key with `env` set, none of which changes its exit code. `start` also refuses `--headless`, `--once`, and a machine with no secret store for the credentials key. Sign-ins and refused requests are logged as `signin.ok`, `signin.refused` and `request.refused`. Remote mode is tested against an in-memory provider only, not against a live OpenID Connect provider behind TLS. See [Remote mode](docs/remote.md) and [The roster](docs/architecture.md#the-roster-one-runner-many-people).
- **MCP clients sign in with OAuth on a remote instance.** Landrace is its own OAuth authorization server for `/mcp`, so no app at your provider is needed. `claude mcp add --transport http landrace https://landrace.example.org/mcp` registers the client, sends you to sign in and to a consent page, and gets a one-hour access token and a refresh token. `/mcp` then serves only that person's items and tools. Registration is open, so every token waits on a signed-in person's approval. The consent page cannot be framed, and Approve needs the page's one-time token, which is bound to the session and to that one request and expires in ten minutes. A refresh token works once and is stored only as a hash. However often it is rotated, its chain ends 30 days after the person approved the client. Every code and token is refused for a person `people.allow` no longer admits. Before each registration, clients older than 24 hours with no live refresh token are removed, and past 1,000 stored clients `/register` answers `400`. Each person keeps at most 16 open MCP sessions, and a 17th closes their oldest. Clients and token hashes are kept under `~/.landrace/credentials/mcp/`, sealed. Not yet checked from a real editor. See [Connecting an MCP client](docs/remote.md#connecting-an-mcp-client).
- **Per-person keys and connections.** A `secrets` or `vars` entry may be each person's own: `{ perPerson: true, env: GITHUB_TOKEN, connection: github.token }`. On a local instance, its value comes from `env` when that variable is set, from `.env` and then your shell, and otherwise from the named field of a connection stored in `~/.landrace/credentials/local.json`. A hook defines a connection with the new `defineConnection`: its id, label, `kind` (`credential` or `identity`) and fields, and optionally `required`, a paste hint, `lifetimeDays`, and `resolve`, `check` and `oauth` functions. `validate` reports `connection.missing`, `connection.unknown`, `connection.expired`, `connection.failed` and `connection.duplicate`, and `landrace status` refuses over each. A credentials file that does not read is named, with each wrong key, and nothing inside it is quoted. Every stored value of 8 characters or more is cut from the log, but a per-person var still reaches comments and prompts unredacted. From 30 days before a connection's end, `start` logs `connection.expiring` once a day. `landrace next` fills a var from the store too. See [Per-person keys](docs/configuration.md#per-person-keys) and [Connections](docs/hooks.md#connections).
- **The Integrations tab.** The board's `#/integrations` page lists each connection the hooks define, with its state (Connected, Not connected, Expired or Not working), why it does not work, and the date it lasts until. A credential that is not connected offers a paste form with the connection's hint, and the connection's `check` judges the value before it is stored. A stored credential offers **Disconnect**. An identity is looked up by your email, never pasted, and its row shows what the lookup found to you alone. A credential's value is never sent back to the page. While a per-person key has no value, a required connection is missing, or a required or stored one has expired or failed, a `start` that serves a board runs nothing: no tick and no preflight run, `/mcp` answers `503`, the page is the tab alone, and stderr lists each `connection.*` problem. `start --once` and `--headless` refuse with the problem instead. Each connect or disconnect rebuilds the runtime: it reads the configuration, the workflows and their hooks lists again, and runs the preflights again. A change to a hook's code still needs a restart. Runs the old runtime started finish under their own item locks. The Claude Code pane has no such tab: while the board shows only the tab, the pane counts each read as failed. See [The board](docs/cli.md#the-board) and [A connection not made](docs/cli.md#landrace-start).
- **Steps can run on your own Claude login.** `claudeConnection`, exported from `.landrace/hooks/claude.ts` beside `new Claude()`, adds a Claude row to the Integrations tab. Paste the token `claude setup-token` prints, and every step and turn, screening runs included, gets it as `CLAUDE_CODE_OAUTH_TOKEN` and uses your Claude subscription's limits rather than the operator's. A step's commands can read it from their environment, so connect only a token you would hand a step. The token lasts 365 days. When Claude refuses it, the step records no round, the row reads Not working with Claude's reason, `connection.failed` is logged, and nothing runs until you paste a new one; it never falls back to the operator's login. Without it, a local instance runs steps on the operator's own `claude` login, as before. An integration on the kit names its connection with `connection: { id, env }`, and the engine hands the stored values to `create` as `ctx.personEnv`. A live run on a real token is not part of `claude-check.mjs` yet. See [Claude Code](docs/integrations.md#claude-code).
- **Identities and forge tokens to connect.** `slackConnection` looks up your Slack member id with `users.lookupByEmail`, which needs `slackBotToken`. `jiraConnection` looks up your Jira account id, which needs the global "Browse users and groups" permission. Both look you up by `people.local.email`, or on a remote instance by the email you signed in with, and the tab shows what they found. `githubConnection` and `gitlabConnection` take a pasted personal access token, checked with `GET /user`, which answers a per-person key that names it, such as `githubToken: { perPerson: true, env: GITHUB_TOKEN, connection: github.token }`. Notion and Codex define no connection. See [Connections](docs/integrations.md#connections).
- **Slack can post as a bot.** With a `slackBotToken` secret, the notifier posts with `chat.postMessage` to `slackNotifyUser`, your direct message with the app, and does not use the webhook even when it is set. The app needs the `chat:write`, `users:read` and `users:read.email` scopes. Without `slackNotifyUser` it refuses, since it has nowhere to post. Slack's own refusal is the error, as `slack: <error>`, such as `slack: channel_not_found`. `slackNotifyUser` may be a per-person key that `slackConnection` answers. See [Slack](docs/integrations.md#slack).
- **Connect with GitLab or GitHub.** When the instance has a forge's OAuth app, named by `gitlabOauthClientId` and `gitlabOauthClientSecret` or by `githubOauthClientId` and `githubOauthClientSecret`, the forge's row in the Integrations tab offers a **Connect with GitLab** or **Connect with GitHub** link in place of the paste form. The app's callback is the board's address followed by `connect/<id>/callback`. The link sends you to the forge's consent page with PKCE and a single-use `state`, valid for 10 minutes and bound to you and the connection. Landrace checks the token it gets back with `GET /user`, as it checks a pasted one, and stores it with its end and its refresh token. A `gitlabBaseUrl` that is not `https://host[:port]` shows the paste form, so no secret crosses plain HTTP. While `start` runs, it renews a GitLab token, which lasts 2 hours, once it is within 10 minutes of its end, logs `connection.refreshed`, and hands the new token to the running hooks. A token the provider refuses to renew marks the row Not working. A GitHub OAuth token does not expire. GitHub is asked for the `repo` scope only, so a build that changes `.github/workflows/` needs a pasted classic token with `workflow`. GitLab's preflight reads an OAuth token's scopes from `/oauth/token/info`. Tested against stub providers only, not against real GitLab or GitHub apps. See [Connect with GitLab or GitHub](docs/integrations.md#connect-with-gitlab-or-github).
- **Events name the person and the workflow.** Every event `landrace start` and `landrace status` log now carries `person`, which is `local` on a local instance, and each workflow's events carry `workflow`, its folder id. `people.local.email` in `landrace.yaml`, written literally or as a `$VAR` reference, adds `personEmail`. `validate` reports a reference that does not resolve, or resolves to an empty value, under `people.local.email`, and `start` and `status` refuse to start over it. `people.local.name` is read and resolved, but nothing carries it yet. Telemetry exports these as `landrace.person`, `landrace.personEmail` and `landrace.workflow`. See [people](docs/configuration.md#people) and [Telemetry](docs/configuration.md#telemetry).
- **Hitting a limit is logged.** `agent.limited`, `{ item, workflow, stage, round, kind }`, says a step's agent failed with text naming a limit: `kind` is `usage`, `rate` or `overloaded`. The step is unavailable as before, and the next tick runs it again. `integration.limited`, `{ integration, status, where, retryAfter? }`, says a tracker, forge, docs or notifier integration got a 429, or from GitHub a 403 with `x-ratelimit-remaining: 0`. Both are `WARN` in telemetry. The kit's new `httpLimit(status, headers)` reads a 429 and its `Retry-After` for an integration's own client, which reports it through `ctx.log`. See [Telemetry](docs/configuration.md#telemetry) and [The kit's functions](docs/hooks.md#the-kits-functions).

The tick button and the theme toggle left the top bar for it; the notifications bell stays, left of the cog. The theme entry reads **Dark mode** or **Light mode**, the mode a click turns on. ### Security

- **Write steps cannot write git's control paths.** A write step must write the repository's shared git directory to commit, and git also reads that directory for what to run, so a planted hook or config would run in Landrace's own git, outside the sandbox and with the forge token, or in your `git pull`. Each write run is now handed, as `denyWrite`, the paths it may not write, whatever `agent.sandbox.deny` says: `config`, `config.worktree`, `commondir`, `hooks/` and `info/` in the common git directory; `config`, `config.worktree`, `hooks/`, `info/`, `commondir` and `gitdir` in each worktree's admin folder; and the worktree's own `.git` file. A path not there yet is listed too. The Claude integration keeps the run from writing any of them. Landrace's git finds a worktree's admin folder itself and takes the common directory from your checkout, never from the admin folder's `commondir`. Before a step, a turn, `agent.worktree.setup` or a pairing uses a worktree, Landrace checks its admin folder: the worktree's `.git` file must point at it, its `commondir` must name the repository's common directory, and it must hold no `config`, `hooks/` or `info/`. Otherwise the run is refused, or the pairing is not handed out, naming the file. An admin folder holding `config.worktree`, or no admin folder naming the worktree, or two, halts the item. Refs and history, a filter you already configured, a `core.hooksPath` pointing into the repository, and submodules are not covered, and the docs list commands to inspect a repository a step has written to. `scripts/claude-check.mjs` gains a third paid turn that tries each path. See [Git write rules](docs/security.md#git-write-rules).
- **Stored credentials are sealed at rest.** Every file under `~/.landrace/credentials/` is encrypted with AES-256-GCM, under one 32-byte key the operating system keeps, with a fresh IV on each write. The file's path is sealed in with it, so a file copied over another person's does not open. A copied disk, a backup or a copied home folder therefore holds no token. Before it reads any file, `start` seals each plain file in place. While there is a key, a plain file is refused, since anyone who can write the folder could put one there: stop `start`, and the next one seals it. A file that does not open is refused, named, and never written over. `validate`, `status` and `next` read under the key that is there and never make one. The servers `start` hands a step or a pairing are told which store holds the key, never the key itself. The Keychain and the Secret Service hand the key to any process of the same user, so a step's shell can still ask for it; a systemd credential is the one source a step is denied. Tested against fakes of `security` and `secret-tool` and a folder for systemd, not against a live Keychain, Secret Service or systemd unit. See [Sealed at rest](docs/security.md#sealed-at-rest).
- **People's steps are kept apart on a remote instance.** Each person's worktrees are cut in a folder of their own, `$TMPDIR/landrace/<repo>/worktrees/<person id>/`. As each step starts, it is denied every other folder there, including one whose person has left the roster, and the Claude Code sessions of runs in those folders, besides `~/.landrace/credentials` and the `.env`. A path no rule can hold refuses the run, and so does an agent that cannot keep the list, such as Codex, while any other person's folder is there. Each person's agent activity goes to a log of their own, which the item panel reads only for its caller. A step's sub-items are filed with that step's person's connections. `agent.isolation: none` is refused. The repository's `.git`, the rest of `$TMPDIR/landrace/<repo>/` and the operating-system user stay shared. For an integration on the kit, `ctx.denyPaths` answers `{ always, people, found, key }` as each run starts, the kit adds it to `plan.sandbox.deny`, `transcriptsUnder(dir)` names where the agent keeps its sessions, and `sandboxProblems` is asked again with those paths. A step refused another person's worktree on a real run is not yet checked. See [People on one instance](docs/security.md#people-on-one-instance).

## [1.8.0] - 2026-11-03

### Added

- **Agents commit as a configured identity.** `agent.git: { name, email }` in `landrace.yaml` names the author and committer of every commit an agent makes, in place of the `user.name` and `user.email` from your `~/.gitconfig` or the repository's config. It sets `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL` for every step and turn, for every coding agent built on the kit. When the forge token belongs to a bot, the pull request and its commits now name the same account, so a forge rule that refuses approval from anyone who committed to the pull request no longer stops you approving the agent's work. Each value may be a `$VAR` or `${VAR}` reference, resolved from `.env` and then your shell, so each developer's instance can name its own identity. `validate` reports an unset or empty variable under `vars`, and an `agent.git` that is not `{ name, email }` under `executor`; `landrace start` refuses to start over either. A hook that commits onto an item's branch passes the kit's new `gitIdentityEnv(ctx)` to its own git, so its commits name the same identity. A commit's signing key still comes from your own git config, and a worktree's `setup` commands get no identity. Unset, nothing changes. See [Who commits](docs/configuration.md#who-commits) and [The kit's functions](docs/hooks.md#the-kits-functions).

## [1.7.1] - 2026-10-28

### Fixed

- **`landrace mcp` connects within a client's timeout.** Before it answers the client, the server lists every distinct tracker once, so a tracker it cannot read stops it before it connects. It listed them one after another, so a workspace of several trackers took their sum, about 34 seconds with four workflows, past Claude Code's default 30-second connect timeout, and no tool loaded. It now lists them all at once, so startup takes as long as the slowest tracker, and any one that fails still stops it. A client that still gives up first can raise its timeout: in Claude Code, `MCP_TIMEOUT` in `~/.claude/settings.json`. See [`landrace mcp`](docs/cli.md#landrace-mcp).

## [1.7.0] - 2026-10-12

### Added

- **Branch variants.** `branchVariants` in `landrace.yaml` names variants of the item branch, each `<branch>-<name>`: `branchVariants: [retro]` gives item 7 the branch `landrace/7-retro`. A stage and its `branch.push` and `pull.*` effects may name a variant, and the GitHub, GitLab and in-memory forges tie a pull request from one to its item, with one query per branch, as the new relationship type `follows-up`: `rel.implements` and the forge's `threads`, `diff` and `ci` briefings read the item branch's pull request alone. The board lists it under the item. A variant's pull request never satisfies the item branch's `pull.open`. A head that reads as two items, such as `landrace/7-retro` with both `7` and `7-retro` known, halts a read and is left out of a listing. `validate` and `start` refuse a name that is not lower-case letters and digits, or is named twice, under `branch`. The kit's `itemsNamedBy` now takes a list of templates, and `itemBranchesOf` gives them. See [Branch variants](docs/workflows.md#branch-variants).
- **A pull request's own title and description.** A `pull.open` effect, in a stage's `on_enter` or a step's route, takes an optional `title` and `description` that replace the forge's `pull.title` and `pull.description` for the one pull request it opens, so a retro's second pull request on an item no longer reads like the feature's. `title` names `{item}` and `{title}`; `description` is the template text itself and names `{item}`, `{link}` and `{spec}`. `validate` refuses any other placeholder, or a value that is not a string, under the new `pull-text` rule. With neither field, nothing changes. A pull request is still found by its branch, never its title. `BaseForge`'s protected `opening` now takes the effect as well as the context. `createExternalState` takes `forge: { pull, root }`. See [Effects](docs/workflows.md#effects).
- **Retry a failed step at a `closed: run` stage.** A `closed: run` stage, such as a retro, may list itself with `retry: only`: `{ stage: retro, retry: only }`. A round that failed there can then be retried with the board's Retry, or with `landrace_goto` naming the stage. The step runs once more on the next tick, and the item stays closed and at the stage. Before, a failed retro could never run again. `validate`'s `closed-run` rule accepts that one entry. It still refuses a plain goto or a route `goto` into the stage, and a `retry: only` entry naming it from another stage. `cycle-bound` does not ask that entry for a cap. On a closed item, every other goto, a Retry where nothing failed, and Clear & retry are refused, each saying which condition failed. The board offers this Retry on every closed item at such a stage, because its labels cannot show whether the round failed, and "Go to step…" never offers the stage. See [Sending an item back](docs/workflows.md#sending-an-item-back-goto-and-retry).

### Changed

So the plugins you enabled for yourself no longer run in `build`, `fix-review` or `retro`. A step gets `agent.plugins`, or its own `plugins`, instead. Your own `sandbox.*` settings no longer reach a write step either. See [Integrations](docs/integrations.md#claude-code).
- **Write steps follow the repository's commit rules.** The shipped `build`, `fix-review` and `retro` prompts tell the agent to find and follow the repository's commit conventions: a commitlint configuration, `commit-msg` hooks, a contributing guide. `retro: lessons from #N` is the retro's subject only when nothing says otherwise.
- **Markdown on Jira is rich text.** Comments and descriptions are written as ADF headings, lists, fenced code blocks with their language, inline code, bold, italic and links, not as one paragraph of raw Markdown. Reading turns the same set back into Markdown.

### Fixed

- **Worktrees start from `origin`'s default branch.** A new item branch, and a stage with no branch, start from `origin`'s default branch, fetched just before, not from your checkout's `HEAD`. A checkout you have not pulled, or one with another branch out, no longer gives steps stale or unrelated code. A fetch that fails fails the round. A repository with no `origin` remote keeps `HEAD`. See [Workflows](docs/workflows.md#the-items-branch).
- **GitLab checks settle on merged results pipelines.** A merged results pipeline runs at a merge commit. It now counts when the head is one of that commit's parents, so `ciPending` no longer stays `1` for ever on a project that uses them.
- **GitLab checks combine every pipeline on the merge request's head.** The pipeline GitLab makes of tools' commit statuses, a scanner's or an AI reviewer's, no longer stands in for the head's other pipelines by being the newest: it counts beside them. Any failed pipeline means `failure`, any still running means `pending`, and a page of 100 that the head's pipelines fill never reads `success`. The CI failures a prompt reads list the failed jobs and failed commit statuses of every pipeline on the head. Tools' commit statuses count as CI unless the new `reviewers` option names them.
- **Jira's `childType` is checked only where children are made.** The preflight checks it only when a loaded workflow has a step declaring `items:create`. A project that names its sub-task type `Sub-task`, or has none, now starts. A preflight's context carries `capabilities`, what the loaded steps declare.

## [1.1.0] - 2026-10-03

### Added

- **Install with `npm i -g landrace`.** A hook's `landrace`, `landrace/hooks`, `landrace/kit`, `landrace/testing` and `landrace/integrations/<vendor>` imports now resolve to the copy of Landrace that is running, so a project needs no `node_modules` for its hooks, and one process never loads a second landrace from the project's own. A hook that imports an export an installed copy lacks says to update Landrace rather than rebuild it.
- **Pairing in the README.** A key concept of its own: working a step together with the agent in your terminal, from the board or with `landrace_pair`.

### Changed

- **`landrace update` updates the copy that is running.** The project's dependency only when the project's own `node_modules/landrace` is the copy running; the global install otherwise, even when the project's `package.json` lists `landrace`.
- **The README's quick start installs Landrace globally** and drops `npx`.

## [1.0.0] - 2026-10-03

### Added

- **The decision engine.** A pure core that derives an item's whole state from its tracker on every run, with no database, and routes each step's output through explicit rules in a workflow file; ambiguity halts the item instead of being resolved by order. `landrace validate` proves a workflow sound before it runs: every loop bounded by a counter, no dead ends, no item two stages' identities both place, no field nothing provides.
- **The CLI.** `landrace start` polls the tracker and works items with per-item locks, `status` says where each item is and why, `validate` checks a workspace, `next` gives the decision for a snapshot with no I/O, and `mcp` serves operator tools over stdio: list, create, update and relate items, reply, ask, resolve, pair, and send an item back to a step.
- **The full-cycle workflow.** From an item to a merged pull request through a spec a person approves, a build, publishing the branch and its pull request, an agent's code review and fix rounds over the review threads, and a person's review and merge. One judge reads every reply, a person can send an item back to any step its stage lists, a retro learns from an item that had to be corrected, and a spec can be written together with Claude Code in a pairing.
- **Workspaces with several workflows.** A workspace holds `.landrace/workflows/<id>/`, each with a name, a description and the labels it admits, and one `landrace start` runs them all. Each open item is claimed by exactly one workflow; two claims, or one id from two sources, halt and name both, and `validate` reports, and `start` refuses, workflows whose claims certainly overlap. A step file can extend another, section by section.
- **The fastlane workflow.** For a change small enough to need no spec: an item labelled `lr:auto` and `lr:fast` goes from its own text to a merged pull request with no person, unless it halts, a cap is reached, or the change touches a protected path, which a person must merge.
- **Forge CI and a guarded merge.** A pull request's checks are read on its head, and a failed check's log is briefed to the build. `pull.merge` merges only on green checks, only at the head the review read (`reviewedBy`), and never a change to a protected path (`refuse`). Only an item's own `landrace/{item}` pull request counts as its work.
- **Item relationships and the waiting gate.** Items are related as `blocked-by`, read and written as issue dependencies on GitHub and as "Blocks" links on Jira, and through the MCP tools on create and update. Both shipped workflows wait for an item's blockers before building, and send it to a person when a blocker was dropped, cannot be read, or is on a cycle.
- **Splitting work into sub-items.** A step declaring `items:create` gets one bound tool to file children under its item, which can be ordered by `blocked-by`; a re-run closes the children it no longer files.
- **The board.** `landrace start` serves a triage page on loopback: a Needs You home across every workflow and a page per workflow, each item's tree of sub-items, pull requests and specs in lanes, and a panel per item with its activity, conversation, relationships and replies. Retry, "Go to step…", "Clear & retry", Refresh and every other write the page offers are guarded against other origins; a Chat menu opens the item in Claude Code, Cursor or Codex; browser notifications say when an item needs you.
- **The integration kit and its integrations.** `landrace/kit` holds what every integration shares: `BaseExecutor` for coding agents, and `BaseTracker`, `BaseForge`, `BaseDocs` and `compose()` for trackers, forges and docs sites. Landrace ships Claude Code and Codex as coding agents, GitHub as tracker, forge and docs (GitHub Pages), GitLab as a forge, Jira as a tracker, Notion as docs, and Slack as a notifier. `landrace/testing` drives a workflow over an in-memory tracker, forge and docs.
- **Security.** Every step that can act, and every typed conversation turn, is screened before it runs; a refusal stops the item in Screened for a person to read and clear. A step's declared capabilities are enforced on its worktree, a write step's commands run in the agent's OS sandbox, writing only to its worktree and the repository's git directory and reaching only the hosts `agent.sandbox` allows, the agent never holds the tracker's token, and text Landrace did not write is escaped so it cannot forge control state.
- **Versions and updates.** `landrace version` (and `--version`) prints the version and whether npm has a newer one; `landrace update` updates the project's own dependency with its package manager, or the global install; `landrace start` says when a newer version is out. The check asks npm's registry once, gives up after two seconds, and is off in CI or with `LANDRACE_NO_UPDATE_CHECK=1`.
- **Notifications and telemetry.** A `notify` block tells a person, through a notifier hook, when an item comes to rest needing them. `--telemetry` exports the engine's events as OpenTelemetry log records.
