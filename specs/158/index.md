## Problem

The fastlane retro commits to `landrace/{item}` before the merge. When a person or auto-merge merges first, the retro either never runs or pushes to a branch that is already merged, and the lessons are lost with nothing reported. `validate` blocks the fix: a stage's `branch` must be the item branch, and a `closed: run` stage takes no branch and plans no `branch.push` or `pull.open`.

## Decisions

Flow:
1. Operator sets `branchVariants: [retro]` in `.landrace/landrace.yaml`.
2. A fastlane item merges after friction. `done` closes it, and its one retro trigger moves it to `retro`.
3. The retro runs once, on `landrace/{item}-retro`, cut from the default branch. `learned` → route pushes it and opens a pull request titled `{item}: retro lessons` (#159). `nothing` → a comment only, nothing published.
4. The board lists that pull request under the item. The item stays at `retro`, closed.
5. Reopened at `retro` → `stuck`, a person's turn.

Choices:
- A variant is `<item branch template>-<name>`. Declared in `landrace.yaml` because a forge reads only `ctx.config`. The suffix form keeps every variant derived from the item branch.
- A name matches `[a-z0-9]+`, is unique, and its filled template passes `branchTemplateProblem`.
- A forge ties a head to an item through any template. A head that reads as two known items (`landrace/7-retro`: item `7-retro`, and variant of `7`) → `read` halts, `list` drops it, as today.
- A variant pull request never satisfies the item branch's `pull.open`: `pullsFrom` matches `state.branch` exactly. Pinned by a test.
- A `closed: run` stage may name only a variant, never the item branch. It plans only `branch.push` and `pull.open`, both on its own branch.
- Fastlane: `merge` drops the friction gate. These go: the `ci`→`retro` trigger, `retro`→`code-review`, `retro`→`stuck` "closed during the retro", and the halts' `retro` goto entry. #154's caps stay.
- Retro trigger: `run.stage: done`, `node.closed: done`, `run.lastOutputValid: null`, `run.counters.retro < 1`, the friction `$or`. No other trigger reads `done`.
- At ship time, closed fastlane `done` items from the last 30 days that had friction and no retro get one paid retro each. Open items at `retro` go to `stuck`: their old retro commit needs "Go to step… code-review". This is accepted and documented.
- Closed `done` items are read on every tick, because a listing cannot judge the trigger. Accepted.
- Retry of a failed post-close retro belongs to #160.

## Technical design

- `src/config/schema.ts` — `branchVariants`, default `[]`.
- `src/conventions.ts` — `variantBranch`, `branchVariantProblem`.
- `src/config/load.ts` — `configProblems` reports variants under rule `branch`.
- `src/workflow/validate.ts` — `validate` takes the variants. `itemBranchProblems` accepts the item branch or a variant. `closedRunProblems` applies the variant-only rule.
- `src/cli/validate.ts`, `src/cli/start.ts` — pass `branchVariants`.
- `src/kit/forge.ts` — `itemBranchesOf`. `headOf` and `itemsNamedBy` take a list of templates. `pullsNaming` returns every head.
- `integrations/github/forge.ts` — one `ITEM_QUERY` per head; forks dropped and page bounds applied per head.
- `integrations/gitlab/forge.ts` — one `source_branch` query per head.
- `src/testing/external-state.ts` — `MemoryForge.pullsNaming` matches every head.
- `.landrace/landrace.yaml` — `branchVariants: [retro]`.
- `.landrace/workflows/fastlane/workflow.yaml` — the changes above; header rulings rewritten.
- `.landrace/workflows/fastlane/steps/retro.md` — its own `output` routes. The prompt says the branch is fresh and Landrace pushes it.
- `docs/configuration.md`, `docs/workflows.md`, `docs/validate.md`, `docs/integrations.md` — updated to match.

## Done when

- `landrace validate` passes on the shipped workflows. Without `branchVariants`, it fails `branch`, naming `landrace/{item}-retro`.
- `validate` refuses a `closed: run` stage on `landrace/{item}`, and one that plans `pull.merge`.
- `configProblems` refuses the variant names `Retro` and `a/b`, and a duplicate.
- The memory, GitHub and GitLab forges tie a `landrace/7-retro` head to `7`. The board lists it under `7`.
- `read` halts when `7` and `7-retro` are both known.
- With only `landrace/7-retro` open, `pull.open` on `landrace/7` is unsatisfied.
- Harness: an item merged after a fix round closes at `done`. The retro runs once, pushes `landrace/7-retro` and opens one pull request titled `7: retro lessons`. Later ticks run nothing. A `nothing` answer pushes nothing.
- `tests/workflow/fastlane.test.ts` sweep out of `done` varies `node.closed` (null, done, dropped), the `retro`, `build`, `fix-review` and `triage` counters, and `run.lastOutputValid` (null, false). Only the retro trigger fires, and only when exact. Out of `retro`, an open item with null `run.lastOutputValid` goes to `stuck` only; a closed item goes nowhere.
